# Contributing to AeroGuide

## Ground rules

1. **Never invent data.** Live positions, schedules, terminal assignments, lounge hours, facilities and card benefits must come from a cited source, or be marked `unverified` or `unavailable`.
2. **Never commit secrets.** Use `.env` files (git-ignored) and the platform secret stores.
3. **Keep the app runnable** after every change.
4. **Open data and free tiers only.** AeroGuide is non-commercial with a zero budget. Don't add paid services or proprietary data sources.

By contributing, you agree that your contributions are licensed under the [MIT License](LICENSE).

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/): `feat(scope):`, `fix:`, `docs:`, `chore:`, `test:`, `ci:`, `refactor:`. Scopes include `web`, `api`, `flights`, `airports`, `lounges`, `cards`, `db`.

## Pull requests

- One logical change per PR, with a description of what changed and how it was tested.
- CI must be green (lint, types, tests, seed validation).
- Update the relevant docs in `docs/` and add an ADR if a decision changes.

## Content contributions (airports, lounges, cards)

Content is edited as YAML seed files ([ADR-0007](docs/decisions/0007-content-as-reviewed-seed-files.md)). Each change must include:

- the **source URL** (an official airport, AAI, airline, bank, lounge operator or programme page),
- the date you checked it,
- `verification_status: verified` only if the fact came from that official source.

For card policy changes, **add a new policy version** with `valid_from`. Never edit an existing one.

The weekly `data-check` issue lists records due for re-verification and sources whose content changed. These are a good place to start.

### Adding airport content

Files live in `apps/api/data/`:

| File | What it holds | Edit by hand? |
|---|---|---|
| `airports.yaml` | Codes, names, cities, coordinates for every Indian airport with scheduled service | **No.** Generated by `scripts/build_airport_data.py` from OurAirports |
| `sources.yaml` | Every source cited anywhere, with a `key` | Yes |
| `airlines.yaml` | Airlines used in terminal assignments | Yes |
| `airport_guides/{IATA}.yaml` | Terminals and terminal airlines for one airport | Yes |

To add a terminal:

1. Open the airport operator's official page that lists the terminal. Add it to `sources.yaml` if it isn't there (`source_type: official_airport`, or `aai` for AAI airports, `airline` for an airline's own page).
2. Add the terminal under `terminals:` in the guide, with a `provenance` block:

   ```yaml
   terminals:
     - code: T1
       name: Terminal 1          # as the source names it
       role: domestic            # domestic | international | mixed, as the source states it
       provenance:
         status: verified        # only if you read it on that source today
         source: del-official    # key from sources.yaml
         verified_at: 2026-11-20
         verified_by: your-github-handle
       airlines:
         - airline: ABC          # ICAO code, must be in airlines.yaml
           operation: domestic   # domestic | international | both
           scope_note: null      # copy the source's wording for partial assignments
           valid_from: 2026-11-20
           provenance: { status: verified, source: abc-airline, verified_at: 2026-11-20, verified_by: your-github-handle }
   ```

3. Run `pnpm seed:check`. It rejects a `verified` record without a source, date and checker, a verified record that cites a secondary source, unknown keys and codes, and typos in field names.
4. Open a PR. The source URL is in the diff, so a reviewer can check it.

If you can't find an official source, leave the section empty. The site says "Not yet verified" instead of guessing. Use `status: unverified` (with a source) only for facts you have a lead on but haven't confirmed.

Merged changes reach production through `.github/workflows/deploy-data.yml` (migrations, then seed).

### Adding lounges and cards

Two kinds of fact are kept apart, each with its own source:

- **What a lounge accepts** (`apps/api/data/lounges/{IATA}.yaml`): from the lounge operator's, programme's or airport's own page.
- **What a card grants** (`apps/api/data/cards/{bank}--{card}.yaml`): from the bank's own card page or its most important terms document.

The checker joins them. The research list for the first cards is [docs/research/card-launch-set.md](docs/research/card-launch-set.md).

Before you start, add the programme to `access_programs.yaml` and each page you read to `sources.yaml` (`source_type: lounge_operator`, `network_program` or `bank`).

A lounge (example values, not a real lounge):

```yaml
iata: DEL
lounges:
  - slug: example-lounge-del-t1     # unique: name, airport, terminal
    name: Example Lounge            # as the source names it
    terminal: T1                    # as the source names it
    scope: domestic                 # domestic | international | both
    side: airside                   # airside (after security) | landside
    direction: departures           # departures (default) | arrivals | transit
    location_text: "Level 2, near gate 10"   # quoted, only if stated
    opening_hours: { mode: 24h }    # or { mode: weekly, periods: [{ days: [mon, tue], open: "05:00", close: "23:00" }] }
    amenities: [wifi, food]         # codes from amenities.yaml, only what the source states
    provenance: { status: verified, source: example-operator-page, verified_at: 2026-11-20, verified_by: your-github-handle }
    accepts:
      - program: example-lounge-programme
        valid_from: 2026-11-20
        provenance: { status: verified, source: example-operator-page, verified_at: 2026-11-20, verified_by: your-github-handle }
```

A card (example values, not a real card):

```yaml
slug: example-bank-voyager
bank: example-bank                  # slug from banks.yaml
network: visa                       # code from card_networks.yaml; leave out if the bank doesn't say
name: Voyager
product_url: https://example.org/cards/voyager
provenance: { status: verified, source: example-bank-voyager-page, verified_at: 2026-11-20, verified_by: your-github-handle }
policies:
  - scope: domestic                 # one version per scope at a time
    valid_from: 2026-07-01          # the date the bank says the benefit applies from
    summary: 2 visits a quarter after spending ₹50,000 in the previous calendar quarter.
    rules:
      - { type: program_entitlement, program: example-lounge-programme }
      - { type: visit_quota, count: 2, period: quarter }
      - { type: spend_gate, amount: 50000, window: previous_calendar_quarter }
      - { type: entry_method, method: card_swipe }
    provenance: { status: verified, source: example-bank-voyager-page, verified_at: 2026-11-20, verified_by: your-github-handle }
```

Rules:

- **Rule types:** `program_entitlement`, `visit_quota`, `spend_gate`, `guest_allowance`, `airport_restriction`, `entry_method`, `fee` and `add_on_cardholders`. Each has fixed fields, and an unknown field is an error.
- **Informational rules:** `entry_method`, `fee` (`{ type: fee, amount: 2, currency: INR, applies_to: cardholder | guest, refundable: true }`) and `add_on_cardholders` (`{ type: add_on_cardholders, covered: true, shares_quota: true }`) are shown with the answer and never change it. Use them instead of `unmodelled_terms` for fees and add-on rules, so a small charge doesn't turn every answer into "depends". Leave out `refundable` or `shares_quota` when the bank doesn't say.
- **Unclear wording:** if the bank's wording can be read two ways (for example "previous quarter" without saying calendar or billing), add `ambiguous: true` to that rule. The checker then answers "depends", never "yes".
- **Conditions no rule type captures:** quote them in `unmodelled_terms`. Every answer for that version becomes "depends".
- **Benefit changes:** end the old version with `valid_to` (the first day the old version no longer applies) and add a new one. Never rewrite a past version. Versions of the same card and scope can't overlap.
- **Checking your work:** run `pnpm seed:check` before opening the PR.
- **Imported cards waiting for a check:** 61 card files start with the comment "Unverified: imported from a third-party lounge tracker". Each cites the page the tracker relied on, usually the bank's own. To verify one, read that page (and the bank's terms PDF), rewrite the rules from what the bank says, remove the tracker's wording from `unmodelled_terms`, and set `status: verified` with your check date. Until then the checker answers "depends" for these cards, never "yes"; a test enforces this.
